# Study 04 — loop protocol

Written 1 October 2026 from Anjor's brief, `loop/SETUP_PROMPT.md`, and his decisions of that date, and brought in line with the final runner and launcher on 2 October 2026.

Every iteration of the Study 04 loop reads this file first and follows it. Each iteration is a fresh, unattended session with no memory of earlier ones. The repo is the only memory, so all work must end up committed and pushed. Nobody can answer questions during the session. Anjor reads the results afterwards and can veto them.

Three failures matter most: money spent without anyone noticing, a gate passed on a hopeful reading, and work lost between sessions. Most of the rules below guard against one of them.

You cannot change this file. A commit that touches it makes the runner stop the loop, because the loop must not loosen its own rules. If a rule here is wrong or blocks all progress, that is a hard stop (§3).

Commands run from the repo root, which is your working directory, so paths in commands are spelled out from there (`studies/04-phase-space-helicity/...`). In the text, a path that does not start with `studies/` is in the study folder `studies/04-phase-space-helicity/`, for example `STATUS.md`, `log/`, `configs/` or `data/scratch/`. The exceptions are `shared/`, `pyproject.toml`, `uv.lock`, `.gitignore`, `.git/` and `.claude/`, and the repo-root `docs/run_log.md`, `paper/`, `infrastructure/` and `CLAUDE.md`, which this file always calls repo-root, because the study has a `docs/` and a `data/` of its own.

## 1. The study

Study 04 asks whether conservation of the KRMHD invariant Γ^± of Chandran, Mallet and Meyrand (2026) changes how compressive free energy moves to high Hermite number m. It injects Γ^± by hand, with a pair forcing on g_0 and g_1 at a fixed relative phase, and compares W(m), the forward and backward Hermite fluxes and Γ(m) between opposite signs of injection and a zero-injection control, in GANDALF at 128³ and M = 128. `PLAN.md` gives the question and the pre-registered outcomes H0, H1 and H2 (§2), the phases and their tasks (§4) and the kill criteria (§7). `SPEC.md` gives the equations in GANDALF variables, the definitions of W and Γ, the forcing, the observables, the run classes and the tolerances (§7). Read both in full every iteration.

## 2. Where you work

- You work in the loop's own clone, `~/repos/anjor/krmhd-research-loop`, on `main`. Anjor works in his own checkout, `~/repos/anjor/krmhd-research`, and you never touch it. Because the clone is the loop's alone, a dirty tree in it can only come from a dead iteration. The runner and `run_forever.sh` refuse to run, and `preflight.sh` fails, unless `git config s04.loopclone` is `true` in the clone. That marker is set in this clone and nowhere else, so that the loop never runs in Anjor's checkout.
- You change GANDALF only in the loop's worktree. The prompt gives its path, normally `~/repos/anjor/gandalf-study04`, and this file calls it `<worktree>`. It is a linked worktree of Anjor's checkout `~/repos/anjor/gandalf`, so the two share their branches and their stash list. Touch only branches named `study04/...`, and never run `git stash` in the worktree, because the stash would land in Anjor's own stash list. You never touch `~/repos/anjor/gandalf` itself.
- `studies/02-collisionality-scan/data` is a link to the data in Anjor's checkout. Read from it, but never write into it, because a write there changes his data.
- Your commits carry the committer name `krmhd-loop`. The runner exports `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` for the session, and also sets `user.name` and `user.email` in the clone's `.git/config`. The committer is how the runner, the launcher and Anjor tell your commits from his, because the author can be set for a single commit, while the committer comes from the session's environment. Never change git config, never pass `--author`, and never set `GIT_AUTHOR_*` or `GIT_COMMITTER_*` yourself, because a commit under another name would hide your work from the guards. A commit made in the clone under another author, with `--author`, by cherry-picking one of Anjor's commits or by replaying his commits, is still judged as yours, and is itself a violation (`identity`) that makes the runner write `STOP`. So never cherry-pick Anjor's commits. A commit with any other committer counts as Anjor's only if a fetch from `origin` brought it into the clone before any local branch held it; one made in the clone under another name, with `git fast-import`, `git commit-tree` or an emptied environment, makes the runner write `STOP` (`provenance`). Take his commits only with `git pull --rebase origin main` (§12), never from a URL.
- `STOP` exists only while the loop is stopped. `WAIT` holds the time before which the runner starts no new session. `compute_ledger.json` holds the A100-hour reservations and charges and is written only by the launcher. `log/` is the iteration log, and `gate_reports/` holds one report per gate evaluation and every critic report. `.loop/` holds the runner's state, including the full transcript of every session. It is not committed, and you never touch it.

### Hard stops

The loop stops and waits for Anjor at these points and nowhere else. They are the decisions he kept for himself: money beyond the cap, the pre-registered question and its tolerances, the loop's own guards, anything that reaches people outside the two repos, and what happens when the study ends or stalls. You stop the loop when:

- a launch would exceed the compute cap;
- the first or second kill criterion of `PLAN.md` §7 is met, as counted in §5 (the third is not a stop: you write up the null);
- a change is needed to a frozen section: `PLAN.md` §2 and §7, `SPEC.md` §7, and, after a launch, the criteria and code frozen with it (§5);
- a change is needed to the loop's guards: `loop/`, any `.claude/` folder, this file, or any `CLAUDE.md` or `CLAUDE.local.md`;
- something would leave the two repos (this one and `anjor/gandalf`): an email, a message to a collaborator, an arXiv submission, a post, a release;
- the study is complete (§15);
- the loop cannot make progress, for a reason it cannot fix.

Which simulations to run is not on this list, because the brief leaves that to the loop: you decide it, within the cap and the rules for run sets in §5. Some refusals of the launcher are hard stops of this list; §9 says which.

To stop the loop:

1. Run `uv run python studies/04-phase-space-helicity/loop/guards.py stop-write --source agent --reason "<reason>" --decision "<the decision Anjor must make>"`. It writes `STOP` and adds a line under `## Blocking` in `QUESTIONS.md`. Keep tool and script names out of the two texts (§12), because the permission rules match the whole command line, quoted text included. Write "remove STOP" rather than the name of the script that does it.
2. Below that line, write the question with the next free Q<n>, the options and your recommendation.
3. Close the log entry with `outcome: hard stop`, commit `STOP`, `QUESTIONS.md` and the closed entry, push and end the session, all without a break. The runner never stashes `STOP`: if it is still uncommitted when the session ends, the runner commits it, with `QUESTIONS.md` when that file only gained lines, pushes it and stops the loop, and if that commit fails it pushes `STOP` straight onto `origin/main`. Commit it yourself all the same, because apart from log lines that only add to the log and a `WAIT`, the runner commits nothing else of yours and stashes the rest, where Anjor does not see it. An entry that ends with `outcome: hard stop` but leaves no `STOP` makes the runner write `STOP` in its place.

The runner starts no session while `STOP` exists, in the working tree or committed at `HEAD`. Anjor resumes the loop with a pushed commit that answers the question and removes `STOP`. Never delete or move `STOP` yourself, in any form, because only Anjor resumes the loop. A commit that deletes it is a violation, and so is a deletion from the working tree or the index that you do not commit: the runner puts such a `STOP` back, records the deletion as a finding (`stop-deleted (uncommitted)`) and writes `STOP` again.

Everything that is not a hard stop, you decide (§8).

## 4. One iteration

The prompt gives your iteration ID (`it-YYYYMMDD-HHMM`, UTC), the start time, the worktree path, and a note on what dead iterations left: every stash entry, and the `loop-*` branches that hold work not on `main`.

1. Orient. Run `git rev-parse --short HEAD` and keep the result as the start commit of your log entry. Read this file, `PLAN.md`, `SPEC.md`, `STATUS.md`, `QUESTIONS.md`, `decisions.md`, `claims.md`, `RUNS.md` and the two newest files in `log/`. Look for Anjor's input (§8): commits since the previous iteration whose committer is not `krmhd-loop`, and `ANSWER:` and `VETO:` lines in `QUESTIONS.md` without a `Handled` note. A veto comes before everything else, and an answer to a Blocking question comes next, because work built on a vetoed gate or decision may be wrong and costs more the longer it goes on.
2. Recover. Do this every iteration, not only when the prompt names a stash.
   - The worktree. Run `git -C <worktree> status --porcelain`. Every iteration commits and pushes its worktree changes, so anything listed was left by a dead iteration. Keep it on a branch of its own, unreviewed: `git -C <worktree> checkout -b study04/recovered-<iteration id>`, `git -C <worktree> add -A`, `git -C <worktree> commit -m "Work left by a dead iteration, saved by <iteration id>"` and `git -C <worktree> push -u origin study04/recovered-<iteration id>`. Then check out the branch you need. Take from it only what you check as new work, and never move it onto a PR branch unread.
   - The stash and the branches. The prompt lists every stash entry as `stash@{n} (<short sha>): <message>`. The runner's own are `loop-stash <iteration id>`, made after a session, and `loop-stash <iteration id>-predirty`, made before one, with `(left on <branch>)` or `(not on main)` added when a session left the clone off `main`, and `(edits during a stopped <operation>)` when a session ended inside a rebase, merge, cherry-pick or revert. An `autostash` entry, or any stash a session made itself, is listed too. Then come the branches that hold work not on `main`: `loop-rescue/<iteration id>` holds commits that a stopped operation, in practice a rebase, had made off `main`, `loop-orphan-<iteration id>` holds commits left on a detached `HEAD`, and `loop-diverged-<date>` holds a local `main` that could not be rebased onto `origin/main`. A runner stub in the log names any other branch a session left. Identify a stash by its sha, not by its position, because positions shift whenever a stash is added or dropped. Inspect a stash with `git stash show --include-untracked --stat <sha>` and `git stash show --include-untracked -p <sha>`, and a branch with `git log --oneline main..<branch>` and `git diff main...<branch>`.
     - If a stash holds `STOP`, or a new item under `## Blocking` in `QUESTIONS.md`, the dead iteration declared a hard stop. First find out whether that stop reached Anjor: `git log --diff-filter=A --format='%h %cn %ad %s' --date=iso <its start commit>..HEAD -- studies/04-phase-space-helicity/STOP` lists the commits that added `STOP` since that iteration started, taking its start commit from its log entry or from the runner's stub. If it lists one, the stop was published, and Anjor has resumed the loop since, because no session starts while `STOP` exists: quote its Blocking question in your entry and treat the stash as an ordinary one. If none did, then unless the log shows that an earlier iteration already declared it again (search `log/` for "Declared by <dead iteration id>"), declare it again now. Read its reason and decision with `git show '<sha>^3:studies/04-phase-space-helicity/STOP'` (without the `^3` if `STOP` was staged in that stash), or from its Blocking item if there is no `STOP`, run `stop-write` (§3) with them, starting the reason with "Declared by <dead iteration id>:", and copy its Blocking question into `QUESTIONS.md`. Leave the stash in place for Anjor. Write a short entry with `outcome: hard stop` that quotes the new reason and lists the stash's files, then commit, push and end. Restoring a stop costs Anjor a look; losing one could carry the loop past a point he kept for himself. Once that stop has been declared again, the stash counts as an ordinary one: never restore its `STOP`.
     - Otherwise restore the sound files with `git checkout <sha> -- <path>`, or `git checkout <sha>^3 -- <path>` for files that were untracked, check them as you would new work, and commit them. A file that was unmerged when the runner stashed it was staged with its conflict markers, so resolve the markers in any such file you restore. Take what is sound from a branch the same way, with `git checkout <branch> -- <path>`, never by cherry-picking or merging it, because a cherry-pick of a commit with another author is an identity violation (§2), and a checkout lets you check each file as new work. Restore nothing under `log/`: the runner has already closed that iteration's entry with a stub, and changing a log line can make it write `STOP`. Quote what matters from the dead entry in your own entry instead, inside a fenced code block, because the runner ignores headings and `End:` lines inside fences (§13). Never restore `compute_ledger.json` from a stash, because only the launcher may write it; if the stash holds a ledger change, the launcher was interrupted, so run `reconcile` and raise it under Open, not blocking.
     - Then drop what you have dealt with. `git stash drop` accepts only the `stash@{n}` form, so run `git stash list` before each `git stash drop stash@{n}` and check that the entry at that position has the sha you mean. Delete a branch you have finished with by running `git branch -D <branch>`, but only once `git branch -r --list 'origin/<branch>'` shows that `origin` has it, because the runner's push of it may have failed; if `origin` lacks it, push it first with `git push origin <branch>`. The pushed copy stays on `origin` for Anjor, because deleting a remote branch is denied. Log what you kept and what you dropped.
3. Check what is in flight. Run `uv run python studies/04-phase-space-helicity/loop/modal_launch.py status`, and if it shows runs in flight, run `reconcile`. If `reconcile` exits with code 2, it could not check some runs and left them as they were: run it again in the next iteration, and raise it under Open, not blocking if it persists. Exit code 4 from either command is the cap hard stop (§9). Then read `compute_ledger.json` and take every run of a launch of kind `gpu` that has `charged_hours` set and a status other than `not_launched`. Fetch and validate (§9) each one that has no row yet in the repo-root `docs/run_log.md`. The row is written only after validation, so this finds a run that was charged but never examined, whatever the status line says. Check open GANDALF PRs and their CI with `gh pr list -R anjor/gandalf --state open` and `gh pr checks <n> -R anjor/gandalf` (§10). This way a finished or failed run is noticed within one iteration, and its hours are charged from its records.
4. Choose one block. If step 1 found a veto, reopening what it vetoes is the block. Otherwise take the next block in `STATUS.md`, and if it is blocked, the next unblocked item in its queue. A block is one coherent unit: a diagnostic with its tests, a derivation with its critic review, a gate's criteria with their critic review, a gate evaluation, a GANDALF change, the launch of a run set, or the analysis of a run set. Do one block only, so that each entry and its commits can be checked on their own. If everything is waiting on Modal runs or CI, set the wait time (§12), write a short entry with `outcome: waiting`, commit, push and end.
5. Write the intent. Open your log entry (§13) with its heading and the `Block`, `Start`, `Intent` and `Expected` lines. Say what you will do, what you expect to see, and what result would change the plan. If you will ask the critic, name its earlier verdicts on the same subject and what is new since (§6). Commit and push the entry at once, as `Study 04 [<iteration id>]: intent: <block>`. The intent is then on record before any result exists, so the results cannot shape it.
6. Do the work, under the repo-root `CLAUDE.md`, the working rules in `PLAN.md` §1 and this file. Configs go in `configs/`, with every physics parameter in them (rule 3 of `CLAUDE.md`). Run IDs follow rule 4, and every run goes in the repo-root `docs/run_log.md`. Analysis reads saved data, so that it can be rerun without rerunning simulations. Diagnostics and forcing go in `analysis/` or `shared/`. Tests for this study go in `tests/` and use the standard library's `unittest`, because pytest is not installed in this repo's environment: `uv run python -m unittest discover -s studies/04-phase-space-helicity/tests -v`. Keep scratch files under `data/scratch/`, which git ignores, so that they never dirty the tree.
7. Verify. Check the block with its own test: the tests for code, the self-check for a derivation, the coded check for a gate. Get a critic review (§6) of every derivation, gate evaluation and interpretation, of each gate's criteria before the data they judge exist (§5), and of every claim you add or change. Record every verdict verbatim in the log and in `claims.md` (§6).
8. Close out. Finish the log entry, ending with its `End:` line. Update `STATUS.md`, `claims.md`, `decisions.md`, `RUNS.md` and `QUESTIONS.md` as the work requires. Stage the files by name, commit as `Study 04 [<iteration id>]: <summary>`, push, and run the final check (§12).

Aim to finish in 90 minutes from the start time. The runner kills the session at 120 minutes, together with every process it started, and most of what is then uncommitted ends up in a stash (§12). Check the clock with `date -u` between steps, and begin the close-out by minute 80 whatever state the block is in. Never end with uncommitted work. If the block is unfinished, commit it labelled WIP (`Study 04 [<iteration id>]: WIP <summary>`), close the entry with `outcome: WIP`, and say in `STATUS.md` exactly what remains. If the last three entries tried the same block and did not finish it, do not try it the same way again: change the approach and say how in the intent, because repeating an approach that failed spends iterations without new information. If three more entries on that block fail, declare a hard stop, because the loop cannot make progress. The runner itself writes `STOP` after six iterations in a row that end as WIP or as a stub, counted since Anjor last resumed the loop.

## 5. Gates

### Quality gates

Gates 1, 2 and 3 check that the work is correct, and the base-state gate (below) checks that the new base state is fit for set A.

- Gate 1 (`PLAN.md` §4, Phase 0): the invariant mapping and `SPEC.md` are accepted. Its coded check runs the derivation scripts' own checks.
- Gate 2 (Phase 1): the conservation residuals converge and the budgets close, to the tolerances of `SPEC.md` §7.
- Gate 3 (Phase 2): ε_Γ flips sign between φ = 0 and π at equal ε_W, to the tolerances of `SPEC.md` §7.

A quality gate passes when three things hold: its coded check in `analysis/gates.py` passes on raw outputs, the critic returns `VERDICT: SUPPORTED` on that evidence, and no kill criterion is met.

Fix a gate's criteria before you see what it judges. Write its operational criteria into `analysis/gates.py`: the numbers that turn `SPEC.md` §7 into a test (for example the fitted slope that counts as "falls as dt²"), the fits and averaging windows, and which runs and files it reads. Get a SUPPORTED verdict that they implement §7, and commit them, before you produce the outputs the gate will judge. If such outputs or their numbers already exist, list in the intent the ones you have seen; Gate 1's derivations exist already, and the runs you make while you write the diagnostics print numbers. After that, never change a gate's thresholds, windows or inputs because of what an output showed. Change them for any other reason only with a new SUPPORTED verdict and a `decisions.md` row that says why. A threshold chosen with the numbers in view is how a hopeful reading gets in.

Commit the gate code before you run it for a decision, so that the report can name the commit that produced it. Evaluate a gate at most once per iteration, so that every evaluation has its own intent, written before it ran. Each evaluation, pass or fail, writes a new report (below). Get the critic's review of the evaluation and commit its report in the same iteration, because the runner accepts a report that says PASS only together with a SUPPORTED review of that gate from the same session (T1, §6). Record a pass in `decisions.md` with the report, the critic's verdict and the commit, list it in `QUESTIONS.md` under For review as a new R<n> item, and carry on. A failed quality gate is normal work: the next iteration diagnoses it and fixes the cause, within the limits on kill criteria below.

### Kill criteria 1 and 2

Kill criteria 1 and 2 of `PLAN.md` §7 are a stop that Anjor kept for himself, so the rule for them leans towards stopping. Count the evaluations of Gate 2 whose coded check fails on the convergence of the Γ residual with dt or M (kill criterion 1), and the evaluations of Gate 3 whose coded check fails (kill criterion 2), since Anjor last answered or vetoed on that gate. An evaluation that the critic found wrong in itself (REFUTED, naming a fault in the gate code or its inputs) does not count; one it could not decide does.

- After the first, the next iteration diagnoses the failure and fixes what it finds, as for any failed gate.
- After the second, ask the critic the kill question itself: give it the criterion's text from `PLAN.md` §7 and the evidence of both evaluations, and ask whether the criterion is met. Unless it returns REFUTED and names a fault in the code or the test that you can fix, declare the hard stop. INCONCLUSIVE is a reason to stop, not to go on.
- After the third, declare the hard stop whatever the critic says.

The hard stop puts the evidence in front of Anjor, and whether the criterion is met is his call.

The base-state gate accepts the new base state, the one GPU product without a Gate 4, from which set A starts (decision 5). Any other quantity is exploratory and cannot change the result, because every extra quantity that could pass on its own raises the chance of a pass under H0.

It needs a ledger that passes its check and whose history only grew (`[ledger]`), frozen items that are unchanged (`[frozen]`), and no file under `loop/` whose content comes from a commit Anjor did not make himself (`[guarded-files]`). It needs a timeout of at least 60 seconds and at most 24 hours, and one of the sets `base`, `A` and `B` (`[set]`). Each config must be a committed YAML file under `configs/`, not a link, whose file name has only letters, digits, `_`, `.` and `-`, because its stem becomes the run label, and whose `entrypoint` names, in the form given under The run code, a committed `.py` file in the study folder with a line `def run(`. No config, and no two configs with the same file name, may appear twice in one launch. Every gate report must pass the report check and fit the set (item 1), the local test record must be committed, and the set must have its row in `RUNS.md`. `uv.lock` must give exactly one GANDALF commit, and a commit that `pyproject.toml` names must be the same one (`[gandalf-pin]`), because the image installs that commit; after a pin change, run `uv lock` and commit both files. The launcher reserves the timeout once per config and refuses if hours used plus hours reserved plus the new reservation would exceed the cap. It commits and pushes the reservation before it calls Modal, and records the app ID and call IDs in a second commit. `smoke` makes the same checks of the tree, the history, the ledger, `loop/` and the pin.

The ledger check walks every commit reachable from `HEAD`, both sides of every merge, and needs `HEAD`'s ledger to extend every ledger version committed since Anjor last reset it. Only a plain commit by Anjor himself that changes `compute_ledger.json` resets it: not a merge, so not a routine pull that includes one, and never a commit GitHub made (a web merge, a squash merge or a web edit), because the loop's own `gh` login can make those. A rollback or a deletion anywhere since then, spread over any number of commits, is refused. `[guarded-files]` holds while the content of a file under `loop/`, or its deletion, comes from a commit by the loop or by GitHub, traced through merges. Anjor clears it by committing the file in his own checkout with different content, a revert or any edit; a GitHub merge of his own branch is fine, a squash merge or a web edit is not.

Most refusals are yours to fix: commit, push or pull, wait for another launcher command to finish (`[lock]`), or correct an argument, a config, a `RUNS.md` row or the choice of reports, and log what you changed. These are hard stops (§3), because only Anjor can resolve them: `[cap]`; `[frozen]`; `[guarded-files]` and `[set]`, which need a change to `loop/`; `[ledger]` for a ledger that fails its check or was rolled back; `[gate-report]` for a second Gate 4 decision, or for a report form that a frozen evaluation writes, since changing it changes a frozen item; and `[history]` caused by a `.git/info/grafts` file. A shallow clone, the other cause of `[history]`, needs only `git fetch --unshallow origin`. When `reconcile` refuses with `[ledger]` because the ledger file has uncommitted changes, the launcher's record commit failed earlier in the session: handle it as its warning says (above).

Check every physics parameter in the configs against `SPEC.md` before you launch, and set Λ explicitly. The header of the Study 2 runner records a lost GPU run: a Hermite run inherited Λ = 1 from an Alfvénic checkpoint and had no cascade.

Estimate the hours from measured wall times. In the repo-root `docs/run_log.md`, the v0.5.0 ν-scan runs at 128³ and M = 128 took 24,228 to 26,058 s on one A100 for 200 τ_A, and later runs of this study add their own. Add the container start-up of each attempt, up to 15 minutes: Modal bills it, but no attempt record shows it, and the ledger never charges it. Write the estimate and its basis in `RUNS.md`. Set the timeout to the estimate plus about a quarter. The timeout is the run's whole budget over all its attempts (below), what the launcher reserves, and what a hung run is charged, so a generous one costs headroom under the cap. Leave headroom of at least one run's timeout below the cap while runs are in flight, because a run whose records show that its budget was not kept is charged more than it reserved (Hours and attempts), and the runner writes `STOP` when hours used plus hours reserved exceed the cap. Keep all runs of one set on one GANDALF commit, so that the set compares like with like. If a planned set does not fit under the cap once finished runs are reconciled, that is a hard stop. Do not shrink or split the set to make it fit, because the cap is where Anjor decides about more compute.

### The run code

A config is a YAML file in `configs/` with every physics parameter and a key `entrypoint`: the path of a `.py` file in the study folder, written exactly as its normalised repo-relative path (`studies/04-phase-space-helicity/...py`), with no absolute path, no leading `./` and no surrounding spaces. The GPU function joins that text, as written, to the repo copy in the container, so the launcher refuses any other spelling with `[config]` rather than let it fail after the GPU has started. The function loads the file and calls its `run(cfg, out_dir, ctx)`:

- `cfg` is the parsed config.
- `out_dir` is `/data/study04/<S>/<run_id>` on the volume `krmhd-benchmark-vol`. Write only there, because the rest of the volume holds other studies' data and the attempt records (Hours and attempts).
- `ctx` has `run_id`, `run_set`, `launch_id`, `attempt_id`, `out_dir`, `volume_root` (the mount, `/data`, which also gives read access to older data such as the Study 2 checkpoints), `deadline_epoch` (below), `repo_commit`, `config_relpath` and `commit()`, which commits the volume.

The container has a copy of `shared/` and the study folder under `/repo`, without `data/`, `log/`, `figures/` and `.loop/`. Both `/repo` and the entrypoint's own folder are on `sys.path`. Inputs such as a base-state checkpoint must therefore come from the volume. The image runs Python 3.12 and installs JAX with CUDA, the GANDALF commit pinned in `uv.lock` with its dependencies, numpy, scipy, h5py and pyyaml. Run code that needs any other package fails on the GPU. On the first attempt the function also saves `launch.json` and a copy of the config in `out_dir`. The launcher names the runs `04_<config file stem>_<YYYYMMDD_HHMMSS>`, in UTC, with one timestamp per launch.

The function imports the run code module, then checks that JAX has a GPU backend, and only then calls `run`. Without a GPU the attempt fails within seconds, with an error that starts `no GPU`, instead of spending its budget on the CPU. The check starts JAX's backends, so set any XLA environment variables at the top of the run code module, not inside `run`. The end record notes the backend and the devices JAX found (`jax_backend`, `jax_devices`).

All attempts of one call share one budget: the launch's timeout T, counted from the start of the run's first attempt, so that a call Modal restarts after a preemption gets only what is left of it. `ctx.deadline_epoch` is that first start plus T less 15 minutes, or plus T/2 if that is later. An attempt that starts after the deadline ends at once, with an end record of status `error` whose error starts `budget exhausted`, and the run code is not called. A watchdog ends any attempt still running at the first start plus T: it writes the end record `budget exhausted (watchdog)`, waits at most 120 seconds for the volume to commit it, and stops the container. One call therefore uses at most T of GPU time over all its attempts, plus container start-up. The end records carry the first start, the deadline and the end of the budget (`first_start_utc`, `deadline_utc`, `budget_end_utc`).

Modal can restart a preempted call, so `run` must resume from the latest checkpoint in `out_dir` when there is one. Call `ctx.commit()` after every checkpoint and diagnostics write, because writes that are not committed are lost if the container is preempted. Close every file under `out_dir` before `ctx.commit()`, because a commit reloads the volume and the reload fails while files on it are open; keep a log file elsewhere, or open and close it for each write. Write a final checkpoint and return before `deadline_epoch`, so that a slow run can be continued and is not lost. Check for NaN, Inf and blow-up as the run goes, and raise an error when you see one, because the loop cannot stop a running app and a broken run otherwise burns its budget. Any exception from `run`, `SystemExit` included, ends the attempt with status `error` and reaches the launcher as a failed call that carries the original type and message; a preemption or a Modal input cancellation ends it with status `interrupted`. Compute and save every quantity that the set's evaluation and `validate_run` read, because the evaluation may not import `krmhd` (§5). Return a small JSON-serialisable summary. It is stored in the ledger as plain JSON, with enum members and other `str` or `int` subclasses turned into plain values.

The local smoke test calls the same `run(cfg, out_dir, ctx)` on the Mac. Use a config that differs from the production one only in size and length (32³ or smaller, M ≤ 64, a few τ_A, under 20 minutes), a local `out_dir` under `data/`, and a stand-in `ctx` with the same attributes whose `commit()` does nothing. Run it twice, with an early `deadline_epoch` the first time, and check that the second call resumes from the checkpoint. Run the set's evaluation on the outputs with `--test`. Write the commands, the config, the wall time, the files written and their checksums to `gate_reports/local_<S>_<iteration id>.md`, and commit it.

### Hours and attempts

The function writes a start record and an end record for each attempt to `/data/study04/_attempts/<S>/<run_id>/` on the volume. They sit outside `out_dir`, so that run code that clears its own folder cannot touch the records that the budget and the charges rest on. Run code never writes there, and never makes an `_attempts` folder in `out_dir`, because `fetch` puts the records in that folder of the local copy. An end record has a status, `ok`, `error` or `interrupted`, and for a failure the error and its traceback. `reconcile` reads the hours from the records; nobody types them in. A finished run is charged its complete attempts as recorded. An open attempt, one without a usable end record, counts from its start to the run's first start plus T, or a full T if its start is unknown, because the budget ends there. The run in total is charged at most T, unless its complete attempts already add up to more than T plus 0.1 hours; then each open attempt counts a full T, because the budget evidently did not hold. A run without any records is charged its full reservation, and smoke runs and runs never sent cost nothing. The ledger's `charge_basis` says which rule applied: `records`, `records+budget`, `records+full_timeout`, `full_reservation` or `none`. An attempt that the watchdog stopped may lack its end record; it is then charged up to the end of its budget. `reconcile` raises a run's reservation only when its records show that the budget was not kept, and only then can a run be charged more than it reserved. Container start-up is billed but in no record, so it is in no charge.

### After a launch

Record the launch ID, the run IDs and the data path in the set's `RUNS.md` row, and the launch ID, the app ID, the run IDs and when you next mean to look under In flight in `STATUS.md`. Set the wait time (§12) only if no other block is ready (§4, step 4), because the runner starts no session while it is set, and step 3 of every iteration checks the runs anyway. While runs are in flight, set it at most three hours ahead, so that a failed run is seen within a few hours. Later iterations run `reconcile`, fetch each finished run, run `validate_run` on it, and update `RUNS.md` (status, and the actual A100-hours from `reconcile`) and the repo-root `docs/run_log.md` (run ID, config, `Modal A100`, wall time, pass or fail, and notes with the launch ID and GANDALF commit). `log_run` in `shared/run_utils.py` writes a row in that format. Explain in the log any run that cost more than its estimate. If `reconcile` warns that Modal has reported no result for a run more than an hour past its budget, the run may be queued for a GPU or stuck: look at its app with `modal app logs <app id>`, and raise it under Open, not blocking if it persists. Its hours stay reserved.

Diagnose a failed run before any relaunch, from its result in the ledger, the end records that `fetch` copies to `data/<S>/<run_id>/_attempts/`, which carry each attempt's error and traceback, Modal's output of the launch in `data/launcher/`, and its fetched outputs. Never relaunch an unchanged config that failed, because it would fail the same way and spend the hours again. Fix the diagnosed cause in the config or the run code, commit the fix, repeat the local smoke test if the code changed, and log the diagnosis. For sets A and B, relaunch a run only as the §7a rule allows, and record the decision in `decisions.md` before you launch it. A relaunch is a new launch with a new reservation, and it counts against the cap like any other. To continue a run past its timeout, launch a new config that resumes from the last checkpoint of the old run. If a launch is still in state `reserved` with no app ID after `reconcile`, the launcher was interrupted. Its app may be running, so do not relaunch its configs, and only Anjor can release its hours. If the next launch needs those hours or those configs, that is a hard stop, because the loop cannot make progress; otherwise put it first under Open, not blocking.

## 12. Git, waiting and the runner

Commit on `main` with subjects of the form `Study 04 [<iteration id>]: <summary>`. Commit as you go, because small commits lose less when a session dies. Stage files by name (`git add <path>...`) rather than with `git add -A`, so that nothing stray goes in, and never stage `compute_ledger.json`, which only the launcher commits. Never run `git stash` yourself, except to inspect and drop the runner's stashes (§4), because a stash is easily lost between sessions. Never cherry-pick Anjor's commits (§2).

Push with `git push origin main`. If the push is rejected, run `git pull --rebase origin main` and push again. Pull only that way: with `--rebase`, from `origin`. A loop merge that does not keep a side's change to a guarded path, `STOP` or the ledger makes the runner write `STOP` (`merge-discard`), as `git pull -s ours` over Anjor's pause would, and a commit that reaches the clone other than by a fetch from `origin` looks like one made in the clone under another name (`provenance`, §2). The last command lists commits on `study04/` branches that are on no remote branch, including those of a branch that was never pushed. It looks only at `study04/` branches because the worktree shares its branches with Anjor's checkout, and his are his. While Modal runs or CI are in flight and nothing else can be done, set the wait time with `bash studies/04-phase-space-helicity/loop/wait.sh <minutes> <reason>`. Minutes run from 0 to 2880, and 0 removes the wait. The script writes `WAIT` but does not commit it, so commit it with your close-out (`git add studies/04-phase-space-helicity/WAIT`). The runner starts no session until the time has passed.

The runner, `loop/run_iteration.sh`, refuses to run unless `git config s04.loopclone` is `true` in its clone (§2). It also writes `STOP` when a `.gitignore` rule that ignores the study's `.loop/` or `data/` is gone, committed or not, before or after a session, because a stash would then take the runner's state and the run data. Copies of both rules live in `.git/info/exclude` too. The `.gitignore` with the `.loop/` and `**/data/` rules must be committed and pushed before the loop's clone is made, or the first runner start writes `STOP`. The runner runs every git command of its own with hooks, fsmonitor and signing off, and it saves a copy of `.git/config` before each session. After the session the runner kills the processes the session left (§11) and seals the transcript. It puts back a `.git/config` that the session changed. If the session ended inside a stopped rebase, merge, cherry-pick or revert, it saves that work as described above and aborts the operation. Commits a session left off `main` go to a pushed branch: `loop-orphan-<iteration id>` for a detached `HEAD`, or the branch the session left. Either way the iteration then counts as a stub in the streak below. It pushes anything unpushed. If that push fails, `.loop/push_pending` records it, and the next runner pushes before its session; a `STOP` that is only local still stops the loop. Then it checks the commits made under the committer name `krmhd-loop`, and the session's transcript. Each finding names its rule. It writes `STOP` when a loop commit

- has an author other than `krmhd-loop` (`identity`), as after `--author`, a cherry-pick or a replay of Anjor's commits;
- touches `loop/`, `.loop/`, this file, or any `.claude/` folder, `CLAUDE.md` or `CLAUDE.local.md` at any depth (`guarded-path`);
- removes or changes a line under `log/` that existed when the iteration started, or that Anjor wrote since (`log-edit`); adding lines at the end is fine;
- changes `compute_ledger.json` other than as the launcher does (`ledger`). Such a commit carries the launcher's subject `Study 04 [launcher]`, touches nothing else, holds a ledger that passes its integrity and structure check, and is a launcher-made successor of each parent's version: it only adds a launch as a reservation, marks a launch `launch_failed` or a run `not_launched` only for a launch reserved in the same session, moves an uncharged run only from `reserved` to `running` or `unknown` or from `unknown` to `running`, never lowers a reservation, and charges a run once, with 0 for a smoke run or a run never sent, the full reservation for a run without attempt records, and otherwise between the hours of its complete attempts and those plus one timeout per open attempt. A deletion of the ledger is never one. Only Anjor releases a reservation that an earlier session left stuck;
- adds Modal code to a code file outside `loop/`, or changes such a file that imports Modal (`modal-code`, §9);
- deletes `STOP` (`stop-deleted`);
- changes or deletes a file under `gate_reports/` that was committed before the session (`report-edit`);
- touches another study's folder under `studies/`, or the repo-root `paper/` outside `paper/phase-space-helicity/` (`other-study`);
- changes a frozen item, or makes it ambiguous with a second heading that matches its key, such as a copy of `## 2. Question` (`frozen`). Every loop commit is checked, so a change that is pushed and then reverted in the same session still writes `STOP`;
- is a merge that does not keep a side's change to a guarded path, `STOP` or the ledger (`merge-discard`).

It also writes `STOP`

- when a commit by another committer did not reach the clone by a fetch from `origin` before a local branch held it (`provenance`), as with a commit made in the clone by `git fast-import`, `git commit-tree` or an emptied environment;
- when your start commit is no longer an ancestor of `main` (`history`: rewritten history);
- when the transcript shows a gate report made to say PASS without its own critic review (T1, §6), a GANDALF merge without `--match-head-commit` and a clean review of that commit (T2, §10), Modal run outside the launcher (T3, §9), or a ledger commit that no launcher run of the session accounts for (T4). For T4, each loop commit that changes the ledger must follow a `launch`, `smoke` or `reconcile` of the same session that started before it, and a `launch` or `smoke` accounts for at most two ledger commits, a `reconcile` for one;
- when the session committed anything and its transcript is missing or unreadable afterwards, because none of these checks can then run;
- when your entry ends with `outcome: hard stop` and there is no `STOP`;
- when the session changed `.git/config`, deleted a committed `STOP` without a commit, or removed a `.gitignore` rule for `.loop/` or `data/`;
- when a frozen item has changed, can no longer be found, or has become ambiguous (`PLAN.md` §2 and §7, `SPEC.md` §7, and everything frozen at a launch);
- when the ledger fails its integrity or structure check, or its hours used plus hours reserved exceed the cap;
- when Modal lists a running app with the loop's name prefix, `s04-loop`, that the ledger does not know; a running app with tasks whose launch the ledger has closed or marked failed, because it spends hours the ledger no longer counts; or an app created during a loop session that the ledger does not know, in any state. With `STOP_ON_ANY_NEW_MODAL_APP=1` in `loop/config.env`, which is the setting, that last check counts every such app whatever its name, so it also stops the loop when Anjor starts an app of his own during a session; with 0 it counts only names that start with the prefix. An app is known by its app ID, and by its name only for a launch that has no app ID yet. A `modal app list --json` that the runner cannot read, a row without a readable `Created at` included, writes `STOP` too, because the check cannot then be made;
- when six iterations in a row end as WIP or as a stub, counted since Anjor last resumed the loop, or the total iteration cap is reached;
- when local `main` cannot be reconciled with `origin/main` or fast-forwarded to it, the clone cannot be put back on `main`, or its tree cannot be stashed;
- when its own setup is broken (the GANDALF worktree is missing, or `loop/settings.json`, `loop/prompt.md` or `loop/config.env` is unusable), or a runner died mid-iteration and that iteration's start commit is unknown;
- before a session, when the clone holds the files or settings listed above.

While `STOP` exists the runner runs only git: neither `guards.py` from `HEAD` nor any `python`, `modal`, `gh` or `claude` that `config.env` at `HEAD` names, because a loop commit that changed them may be why the loop stopped. After a runner crash, the next runner takes the loop files from the commit where the dead iteration started. Resuming accepts `HEAD` as it is, so a loop change to `loop/` that Anjor leaves in place runs from the next iteration. `loop/run_forever.sh` runs a copy of `run_iteration.sh` taken from a commit it trusts, never the file in the working tree: `HEAD` while there is no `STOP`, otherwise a dead iteration's start commit, and at its own start the newest version that the loop did not commit. A change Anjor pushes to `run_iteration.sh` therefore takes effect one iteration after the pull. When a `STOP` could not be pushed, `run_forever.sh` retries `run_iteration.sh --push-only` after every pause until `STOP` is on `origin`, and carries on if `STOP` was removed meanwhile. After a resume, Anjor starts `run_forever.sh` again if it has exited.

The permission rules deny what the loop must not do. If a command is denied, do not retry it, and do not reach the same effect another way, whether by another spelling, a script, a subprocess or another tool. Log it under Surprises and problems. If the block cannot go on without it, take another block, and if no block can, that is a hard stop. Some commands are refused only because they are not on the allow list: compound commands joined with `&&`, `;` or `|`, `cd`, and Python called other than through `uv run`. For these the plain form is fine: one command per call, `git -C <dir>`, `uv run --directory <dir>`, the Read, Grep, Write and Edit tools, and `git rm` for tracked files.

The rules also match quoted text. Free text on a command line, such as a commit message, a STOP reason or decision, a wait reason or a statement of the kill criteria, gets the whole command denied if it contains a guarded phrase. Keep the word "modal" and the names of the loop's scripts and tools out of such text: write "GPU run", "the launcher" or "cloud", and "remove STOP" rather than the script that does it. The guarded phrases include `modal run`, `modal deploy`, `modal serve`, `modal shell`, `modal launch`, `modal app stop`, `modal config`, `modal setup`, `modal secret`, `from modal`, `import modal`, `-m modal`, `modal.App`, `modal.Function`, `modal_app`, `GIT_AUTHOR`, `GIT_COMMITTER`, `core.hooksPath`, `resume.sh`, `pause.sh`, `run_iteration`, `run_forever`, `selftest`, `claude -p`, `pip install` and `sendmail`. Rephrasing such text is not a way around a rule. For the same reason, read files with the Read and Grep tools, because a shell command that only names a guarded thing, such as a grep for `modal_app`, can be denied too. The runner's transcript checks, on the other hand, read a command line the way the shell does: text inside quotes, here-document bodies and comments are not commands, so a commit message that mentions a command does not count as running it, while commands inside `bash -c`, `sh -c`, `eval` and `$(...)` do count, and so does each command of a chain.

## 13. The log and STATUS.md

The log has one file per UTC day, `log/YYYY-MM-DD.md`. Take the date from your iteration ID, even if you finish after midnight, because the runner looks for your entry there. If the file does not exist, start it with the line `# Study 04 loop log — YYYY-MM-DD` and a blank line. Each iteration appends one entry, including iterations that only wait. Entries are append-only. Never edit or delete an earlier entry, or a line of your own entry once it is committed. A later entry corrects a wrong one and says what was wrong.

```
## <iteration id>: <the block, in one line>
- Block: <PLAN.md reference>
- Start: commit <sha>, tree clean | recovered from stash
- Intent (written before the work):
- Expected:
- Did: <commands, scripts, files changed>
- Runs: <run IDs, where, wall time, gate output verbatim>
- Results: <numbers with units, figure paths>
- Critic: <what it was given, verdict verbatim>
- Claims: <IDs added or updated>
- Decisions: <what and why>
- GANDALF: <issue, PR, commit>
- Compute: <local minutes; the line printed by `modal_launch.py status`>
- Surprises and problems:
- For Anjor: <items raised, none of them blocking>
- Next: <next block and why>
- End: <UTC time>, outcome: done | WIP | waiting | hard stop
```

Write the heading and the four lines from `Block` to `Expected` before the work, and commit them. Append the other lines at the close-out, below them and in this order, so that your entry stays at the end of the file. Never commit a line that you mean to fill in later. The runner checks that the log only grows at its end, and a changed line can make it write `STOP`. Write `none` in a field that does not apply. Keep a newline at the end of the file, because appending after a last line that lacks one can show as a change to that line. Before each commit that touches the log, run `uv run python studies/04-phase-space-helicity/loop/guards.py log-check --base <start commit>`; it exits with 0 when the log has only grown since your start commit. Take the `End:` time from `date -u +%Y-%m-%dT%H:%M:%SZ`. The runner reads `- End:` and `- **End:**` alike, reads `outcome: wait` as waiting, and counts an outcome it cannot read, such as the template's list left in place, as WIP. It ignores headings and `End:` lines inside fenced code blocks, which is why a dead entry is quoted inside one, and it closes a fence left open before it appends a stub.

## 14. Never
